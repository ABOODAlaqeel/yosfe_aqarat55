# هيكلية الباك اند (Backend Architecture)

هذا الملف يوضح كيف سيتم تصميم المكونات الخاصة بقاعدة البيانات وإدارة البيانات (Local Backend) باستخدام SQLite في مرحلة "الجزء الثاني" من تطوير التطبيق.

## 1. التقنية المستخدمة

- **SQLite:** قاعدة بيانات مترابطة (Relational Database) محلية ستكون مناسبة جداً لتطبيق "إدارة العقارات" الذي يعمل محلياً بسرعة وبدون الحاجة لإنترنت.
- **الحزمة المختارة:** `sqflite` للتعامل المباشر مع قاعدة البيانات، و `path_provider` لتحديد مسار حفظ الملفات.

## 2. هيكلة مجلد الباك اند (`lib/core/database/`)

سيتم التركيز على نمط (Repository Pattern / DAO Pattern) كالتالي:

- **`DatabaseHelper`**: هذا هو الملف الرئيسي (Singleton Class).
  - مسؤول عن إنشاء قاعدة البيانات لأول مرة (`onCreate`).
  - وتحديثها إن لزم الأمر (`onUpgrade`).
  - ويحتوي على أوامر `CREATE TABLE` لجداول العمارات الشقق والمستأجرين والمدفوعات التي تم تفصيلها في `database_schema_sqlite.md`.
- **Repositories (مستودعات البيانات)** سيتم إنشاء ملف منفصل لكل كيان للتعامل المباشر مع جدوله بطريقة CRUD (Create, Read, Update, Delete):
  - `BuildingRepository`: لدوال مثل إضافة عمارة، إحضار قائمة العمارات، جلب معلومات عمارة محددة.
  - `ApartmentRepository`: إضافة الشقق (دفعة واحدة أو فرادى)، تغيير حالة الشقة لمؤجرة عند إضافة مستأجر.
  - `TenantRepository`: حفظ المستأجرين مع ربطهم بقيم الشقة (الـ `apartment_id`).
  - `PaymentRepository`: تسجيل المدفوعات الخاصة بالإيجارات.

## 3. التعامل مع البيانات الحقيقية من الـ UI

- لا تقوم الشاشة بالاتصال بقاعدة البيانات بشكل مباشر أبداً.
- عند محاولة عرض العمارات، تقوم الشاشة باستدعاء شيء مثل `BuildingRepository.getAllBuildings()`.
- عند نجاح الاتصال وجلب القوائم، تستبدل الـ UI البيانات الوهمية بقائمة البيانات الحقيقية العائدة من هذا المستودع.

## 4. إرفاق وحفظ الصور (للعقود)

- **ملفات النظام (`File`):** سيتم استخدام حزمة `path_provider` للحصول على المسار المحلي (Documents Directory) لحفظ صور عقود المستأجرين المرفقة.
- **في قاعدة البيانات:** لن يتم حفظ الصورة نفسها لتجنب تضخم حجم الـ SQLite، وإنما سيتم تخزين مسار ملف الصورة (`String: image_path`) ليتم استدعاء الصورة منه لاحقاً في بيانات المستأجر.
